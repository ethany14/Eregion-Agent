# 推荐分层与验收标准调整（tiered-recommendations-v1，2026-10-13）

用户明确改变了产品要求：**推荐不必意味着全部资格已确认**。系统可以返回更多相关机会，并写明缺口与待确认条件，由用户自行判断。

本规格覆盖交接报告（`docs/diagnostics/model-owned-search-handoff-20261013.md`）第 7–9 节中的两条旧要求：
- “推荐必须全部个人资格确认”；
- “验收至少 10 条 `personal == met`”。

旧验收结果与旧评估器保持原样，作为历史证据，不重新计分为通过。

未改变的原则：
- 不得把未知描述为满足；
- 不得用低相关岗位凑数；
- 用户明确的“必须满足”“不要此类岗位”优先；
- 分类、资格含义和推荐理由由模型判断；
- 不新增正则、关键词、规则词典、固定分数或年限阈值来裁决。

## 1. 三类推荐（模型结合原始需求、完整 JD、简历与用户陈述判断）

| 类别 | `tier` | 含义 |
|---|---|---|
| 优先推荐 | `priority` | 职位方向、地点、级别匹配；能力证据较充分；没有已知重大资格冲突。允许偏好项差距。 |
| 可以尝试 | `stretch` | 整体相关，但存在技能、经验等能力差距，包括部分岗位必需项缺口。必须逐项写明差距与申请难度，不得宣称已满足。 |
| 待确认机会 | `to_confirm` | 岗位相关，但 GPA、国籍、签证或项目身份、执照、到岗或入职时间等关键个人信息未提供，需要用户确认。 |

边界：
- **GPA：** 简历未写 GPA，不判为不达标；记为待确认项，并写明岗位要求。
- **必需技能缺口：** 可作为 `stretch` 展示，但必须列在 `gaps` 中，不能埋在笼统的 caveat 里。
- **未知的特定资格**（国籍、执照等）：可作为 `to_confirm` 展示。
- **用户已明确不符合的硬性资格：** 不计入可申请机会，用 `decide_job exclude`；已确认不满足的条件仍由代码阻止推荐。
- **不计入结果的岗位：** 已关闭、重复、明显不相关、违反用户明确的地点或级别限制。
- **职位相关性核验（role / location / seniority / vacancy）保持不变：** 它判断岗位本身是否符合用户请求，不是个人资格门。

## 2. 统一契约（最小改动，复用现有推荐记录）

`recommend_job` 增加并保存以下字段：

| 字段 | 内容 |
|---|---|
| `tier` | 推荐类别 |
| `reason` | 推荐理由 |
| `evidence` | 来源证据：岗位原文引用，由代码核验确实出现在已读正文中 |
| `gaps` | 已知差距 |
| `to_confirm` | 待确认条件 |
| `next_steps` | 下一步建议 |

代码自动附加：
- 岗位身份：`application_id`、`title`、`company`、`location`、`url`；
- 核验时间：正文读取时间；
- `match_score` 与 `score_meaning`：评分不可用时写明不可用，不填默认分；
- 资格核验引用。

同一套类别含义由以下各处共用：
- 推荐记录、`decision_brief`、`recommend_job`、`decide_job`；
- 完整与精简提示词（共享常量）；
- 最终回复：按类别分组并给出各类数量；
- 界面标签。

`decide_job` 保留两个取值：
- `exclude`：不展示，例如用户已明确不符合、明显不相关；
- `needs_evidence`：岗位本身信息不足、无法作为机会展示。

个人信息未知不再使用 `needs_evidence`，而改为推荐类别 `to_confirm`。

代码只负责结构、引用、身份、去重、预算与状态一致性，不做语义资格裁决。仍接入唯一 AgentLoop；默认来源 LinkedIn MCP + 招聘板 API，Treg 关闭。

## 3. 验收（新版本 `tiered-recommendations-v1`）

目标：一次交付 10–15 个真实、互不重复、与需求相关、说明充分的岗位机会，三类结果可以共同组成。报告各类数量，不设分类配额。

独立审计分两阶段，预算合计仍为最多 6 次 / 200k 输入 token：

1. **独立判断。** 输入只有原始需求、岗位正文和候选人资料，没有生产标签。审计模型逐岗位判断：
   - 是否真实、当前有效、相关，是否违反用户明确的限制；
   - 自己认为的类别；
   - 重要差距；
   - 待确认条件；
   - 已知不符合的硬性资格。
2. **核对生产交付。** 输入为第一阶段的独立结论加生产交付内容（类别、理由、差距、待确认项、评分）。审计模型逐岗位判断：
   - 分类与理由是否合理；
   - 重要差距或待确认条件是否如实展示；
   - 是否把未知说成满足；
   - 是否把已知不符合的硬性资格说成可申请；
   - 评分是否被误用为资格证明。

计数条件（全部满足才计入）：
- 第一阶段判定相关且未违反用户限制、岗位有效；
- 第二阶段无上述违规；
- 结构检查通过：评分与岗位绑定、URL 与评分出现在最终回复中、不重复、已实际读取。

不再要求 `personal == met`。

## 4. 实验预算与重试

- **累计预算：** 一个付费实验（回放、探针、验收）的全部岗位、阶段、并发与重试共享一个累计账本（实验 ID + 上限）。不能通过创建新 task 重置额度。失败或中途退出的调用也计入。
- **未知用量：** 已发送后断开的调用保留 unknown usage，即使重试成功也不消除。
- **重试：** 仅限可恢复的传输错误或响应格式错误，最多一次。认证、配置、程序错误、取消和预算停止都不重试，也不为得到更有利的语义结论而重试。
- **本次额度：** 需求变化不增加额度。完整验收使用 `expanded` 档：
  - provider 100、LinkedIn 100、输入 1.5M、执行 1500 秒；
  - 审计单独最多 6 次 / 200k。

  不启动无 Jev 的 120 次验收。

## 5. 验证顺序

1. **离线回归，** 覆盖以下场景：
   - GPA 未提供、必需技能缺口、偏好项缺口；
   - 国籍未知、国籍已确认不符；
   - 岗位已关闭、地点冲突、重复岗位；
   - 用户明确要求全部条件满足。

   同时检查单个与批量入口、完整与精简提示词、最终展示是否一致。
2. **真实模型分类与决策回放：** 复用已保存的 JD、简历与评分，不重新抓取、不重复评分；评分失效时明确处理。
3. **摘要使用：** 确认模型能用摘要完成分类、说明风险并继续处理下一批，不反复翻完整报告。
4. **完整真实搜索：** 以上通过后运行一次，目标 10–15 条；不足时如实报告，不自动重复。
