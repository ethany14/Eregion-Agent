# 推荐分层与验收标准调整（tiered-recommendations-v1 → v2，2026-10-13）

> **当前验收版本：`tiered-recommendations-v2`**（第 6 节）。v2 取消一切固定最低数量门槛；第 3 节的 v1 计数口径与“10–15 条”目标仅作为历史版本保留，v1 及更早的运行结果与失败结论原样保留，不按 v2 重新判定。

用户明确改变了产品要求：**推荐不必意味着全部资格已确认**。系统可以返回更多相关机会，并写明缺口与待确认条件，由用户自行判断。

本规格覆盖交接报告（`docs/diagnostics/model-owned-search-handoff-20261013.md`）第 7–9 节中的两条旧要求：
- “推荐必须全部个人资格确认”；
- “验收至少 10 条 `personal == met`”。

旧验收结果与旧评估器保持原样，作为历史证据，不重新计分为通过。

未改变的原则：
- 不得把未知描述为满足；
- 不得用低相关岗位凑数；
- 用户明确的“必须满足”“不要此类岗位”优先；
- 分类、资格含义和推荐理由由模型判断；
- 不新增正则、关键词、规则词典、固定分数或年限阈值来裁决。

## 1. 三类推荐（模型结合原始需求、完整 JD、简历与用户陈述判断）

| 类别 | `tier` | 含义 |
|---|---|---|
| 优先推荐 | `priority` | 职位方向、地点、级别匹配；能力证据较充分；没有已知重大资格冲突。允许偏好项差距。 |
| 可以尝试 | `stretch` | 整体相关，但存在技能、经验等能力差距，包括部分岗位必需项缺口。必须逐项写明差距与申请难度，不得宣称已满足。 |
| 待确认机会 | `to_confirm` | 岗位相关，但 GPA、国籍、签证或项目身份、执照、到岗或入职时间等关键个人信息未提供，需要用户确认。 |

边界：
- **GPA：** 简历未写 GPA，不判为不达标；记为待确认项，并写明岗位要求。
- **必需技能缺口：** 可作为 `stretch` 展示，但必须列在 `gaps` 中，不能埋在笼统的 caveat 里。
- **未知的特定资格**（国籍、执照等）：可作为 `to_confirm` 展示。
- **用户已明确不符合的硬性资格：** 不计入可申请机会，用 `decide_job exclude`；已确认不满足的条件仍由代码阻止推荐。
- **不计入结果的岗位：** 已关闭、重复、明显不相关、违反用户明确的地点或级别限制。
- **职位相关性核验（role / location / seniority / vacancy）保持不变：** 它判断岗位本身是否符合用户请求，不是个人资格门。

## 2. 统一契约（最小改动，复用现有推荐记录）

`recommend_job` 增加并保存以下字段：

| 字段 | 内容 |
|---|---|
| `tier` | 推荐类别 |
| `reason` | 推荐理由 |
| `evidence` | 来源证据：岗位原文引用，由代码核验确实出现在已读正文中 |
| `gaps` | 已知差距 |
| `to_confirm` | 待确认条件 |
| `next_steps` | 下一步建议 |

代码自动附加：
- 岗位身份：`application_id`、`title`、`company`、`location`、`url`；
- 核验时间：正文读取时间；
- `match_score` 与 `score_meaning`：评分不可用时写明不可用，不填默认分；
- 资格核验引用。

同一套类别含义由以下各处共用：
- 推荐记录、`decision_brief`、`recommend_job`、`decide_job`；
- 完整与精简提示词（共享常量）；
- 最终回复：按类别分组并给出各类数量；
- 界面标签。

`decide_job` 保留两个取值：
- `exclude`：不展示，例如用户已明确不符合、明显不相关；
- `needs_evidence`：岗位本身信息不足、无法作为机会展示。

个人信息未知不再使用 `needs_evidence`，而改为推荐类别 `to_confirm`。

代码只负责结构、引用、身份、去重、预算与状态一致性，不做语义资格裁决。仍接入唯一 AgentLoop；默认来源 LinkedIn MCP + 招聘板 API，Treg 关闭。

## 3. 验收（历史版本 `tiered-recommendations-v1`，已被第 6 节 v2 取代）

目标：一次交付 10–15 个真实、互不重复、与需求相关、说明充分的岗位机会，三类结果可以共同组成。报告各类数量，不设分类配额。

独立审计分两阶段，预算合计仍为最多 6 次 / 200k 输入 token：

1. **独立判断。** 输入只有原始需求、岗位正文和候选人资料，没有生产标签。审计模型逐岗位判断：
   - 是否真实、当前有效、相关，是否违反用户明确的限制；
   - 自己认为的类别；
   - 重要差距；
   - 待确认条件；
   - 已知不符合的硬性资格。
2. **核对生产交付。** 输入为第一阶段的独立结论加生产交付内容（类别、理由、差距、待确认项、评分）。审计模型逐岗位判断：
   - 分类与理由是否合理；
   - 重要差距或待确认条件是否如实展示；
   - 是否把未知说成满足；
   - 是否把已知不符合的硬性资格说成可申请；
   - 评分是否被误用为资格证明。

计数条件（全部满足才计入）：
- 第一阶段判定相关且未违反用户限制、岗位有效；
- 第二阶段无上述违规；
- 结构检查通过：评分与岗位绑定、URL 与评分出现在最终回复中、不重复、已实际读取。

不再要求 `personal == met`。

## 4. 实验预算与重试

- **累计预算：** 一个付费实验（回放、探针、验收）的全部岗位、阶段、并发与重试共享一个累计账本（实验 ID + 上限）。不能通过创建新 task 重置额度。失败或中途退出的调用也计入。
- **未知用量：** 已发送后断开的调用保留 unknown usage，即使重试成功也不消除。
- **重试：** 仅限可恢复的传输错误或响应格式错误，最多一次。认证、配置、程序错误、取消和预算停止都不重试，也不为得到更有利的语义结论而重试。
- **本次额度：** 需求变化不增加额度。完整验收使用 `expanded` 档：
  - provider 100、LinkedIn 100、输入 1.5M、执行 1500 秒；
  - 审计单独最多 6 次 / 200k。

  不启动无 Jev 的 120 次验收。

## 5. 验证顺序

1. **离线回归，** 覆盖以下场景：
   - GPA 未提供、必需技能缺口、偏好项缺口；
   - 国籍未知、国籍已确认不符；
   - 岗位已关闭、地点冲突、重复岗位；
   - 用户明确要求全部条件满足。

   同时检查单个与批量入口、完整与精简提示词、最终展示是否一致。
2. **真实模型分类与决策回放：** 复用已保存的 JD、简历与评分，不重新抓取、不重复评分；评分失效时明确处理。
3. **摘要使用：** 确认模型能用摘要完成分类、说明风险并继续处理下一批，不反复翻完整报告。
4. **完整真实搜索：** 以上通过后运行一次；v2 下数量只作报告，不足时如实说明，不自动重复。

## 6. 验收版本 `tiered-recommendations-v2`（2026-10-13，用户再次调整）

用户要求：取消 `minimum_qualified`、“少于 10 条失败”以及其他固定最低数量门槛；数量只作为报告指标，不设各类配额；不为凑数增加无效搜索。三类推荐（第 1 节）与“不把未知说成满足、不隐藏已知冲突”保持不变。

### 6.1 失败条件（只看实质错误）

- **展示的每个岗位**必须：真实已读取、已评分且分数与记录一致、不重复、带类别、URL 与分数出现在最终回复中、未被代码判定为已确认不符合；独立审计（第一阶段）确认职位方向（role）相符，且任何请求字段都不是明确冲突（`unmet`）。地点、级别、在招状态为 `unknown` 时只记录，不判失败。
- 第二阶段核对，以下任一为实质错误：
  - 把未知说成满足；
  - 隐藏已知硬性冲突、重要差距或待确认条件，足以误导用户是否申请（`known_conflict_hidden`）；
  - 理由或证据有原文与简历不支持的陈述（`unsupported_claim`）；
  - 把已知不符合的硬性资格说成可申请；
  - 把评分当作资格证明。
- **合理的类别分歧不判失败**，只在 `tier_disagreements` 中报告；轻微遗漏列入 `minor_omissions`，不判失败。
- **每个已评分岗位都必须有结论**（推荐或 `decide_job`），否则 `scored_jobs_without_outcome`。
- **最终回复审计**（一次调用，计入审计 6 次 / 200k 上限）：对照代码记录的运行事实——来源调用与失败、读取/导入/评分/决策数量、未处理岗位、结束状态——判断回复是否说明了搜索内容与结果少的原因，是否隐瞒或误报抓取失败、未处理候选、预算或异常停止，是否误报岗位、类别、分数或数量。任一不实即失败。结果少或为零本身不失败，但也不能借此回避质量核验。
- 原有运行约束不变：干净结束、usage 完整且无未知、主模型与总输入在档位上限内、无投递与定时任务、审计不超过 6 次 / 200k。

### 6.2 报告指标（不设门槛）

各类展示数与无实质错误数、类别分歧、首个可用结果用时与总用时、provider 调用与 LinkedIn 调用数、输入/输出 token 与未知用量、重复读取（同参数的 LinkedIn 详情读取与上下文翻阅）、重复评分（同一已挂载正文出现第二份评分报告）、审计用量单列。

### 6.3 生产修正（与本版本同时）

`search_recovery.search_request` 原先只识别“find N … positions”这类带数字的请求；不带数字的请求会使候选队列、搜索工具范围、最终回复的 URL/分数核验与来源分页全部失效。现在数字可选（未写时 `count=None`，按宽泛搜索处理），完成门只在用户写明数量时才以数量为依据。未新增关键词或规则。

候选队列的状态一致性（decision-replay-tiered-v2-01 发现）：本轮已尝试但无进展（返回错误或无新证据）的导入/评分项，不再作为下一步列在 `in_progress`，而是列入 `stalled` 并附上次结果；它不再阻挡搜索，模型可在情况变化后重试、带原文证据排除或如实报告。新的用户回合会清除该状态。这只是状态呈现，不规定决策顺序。最终回复审计的运行事实中包含 stalled 列表，回复不得隐瞒。

### 6.4 速度与 token 评价口径（测试前写定，测试后不改）

可比历史（同一合成候选人、同一请求类型，均为 Jev 评分、Treg 关闭）：

| 运行 | 正文读取 | provider 调用 | 输入 / 输出 token | 总用时 | 首个推荐 | 重复上下文翻阅 |
|---|---:|---:|---:|---:|---:|---:|
| run 16（基线档） | 49 | 58 | 557,810 / 76,659 | 535 s | 235 s | 1 |
| expanded-01 | 23 | 52 | 585,620 / 58,644 | 611 s | 无 | 6 |
| expanded-02 | 62 | 98 | 895,688 / 108,753 | 1,068 s | 597 s | 0 |

按实际工作量归一，expanded-02 约为每份已读正文 14.4k 输入 token、1.6 次 provider 调用、17 秒；run 16 约为 11.4k、1.2 次、11 秒。

评价规则：
- 每份已读正文输入 token ≤ 15k、provider 调用 ≤ 1.6 次、用时 ≤ 18 秒：与历史相当；任一项超过历史最差值 30% 以上（> 18.7k、> 2.1 次、> 22 秒）：**需改进**。
- 首个可用结果用时 ≤ 600 秒为与 expanded-02 相当；更长为需改进。
- 以下任一不为 0 即标为浪费、需改进：重复评分、同参数重复的 LinkedIn 详情读取、对同一引用的重复上下文翻阅超过 2 次、已评分岗位未决策就继续搜索后导致结束时仍未决策。
- 上限是保护线，不是消耗目标：未用完上限不是问题；为增加数量而在已无新候选的来源上继续翻页是浪费。

## 7. 验收版本 `tiered-recommendations-v3`（2026-10-14，在 v2 上增加“停止是否合理”）

v2 的全部条件不变（第 6 节），另加：

- **停止合理性。** 最终回复审计（同一次调用，不增加审计次数）对照记录的搜索轨迹判断停止是否合理，并写明依据的具体事实。轨迹包括：各查询的来源总数与已看卡片数、已搜索与剩余的看板、各来源的产出（卡片 → 读取 → 合格 → 推荐）、失败、剩余预算以及模型给出的 `stop_reason`。
  - `premature`：明显值得且成本合理的下一步未做，也没有合理理由。判失败。
  - `borderline`：下一步可行但价值不确定。只记为改进建议。
  - `reasonable`：再搜也不太可能增加相关岗位。
  - 未用完预算本身不是继续的理由；只查一次也可以足够。
- 不规定最低结果数、查询次数或来源数，也不要求耗尽预算。

### 7.1 与本版本同时的生产修正（由主模型判断，代码只呈现事实与结构）

- **重要差距披露。** DraftKings 案例的信息链路完整：机器学习/回归要求以 required、状态 `unknown`（评分器未判定）出现在决策摘要里。问题在于模型把 unknown 当成非差距。共用推荐规则与摘要说明改为：
  - unknown 表示评分器未判定，需自行对照简历；
  - 简历未体现的必需能力写成“简历未体现”（不是“不会”），并说明影响；
  - 先写影响申请决定的差距；
  - 次要待确认项不能代替重要能力差距；
  - 职责只有在岗位要求入职即具备时才算差距。
- **停止所需的事实。** `search_coverage` 紧挨候选队列，给出各查询的来源总数、页数与已看卡片数，看板已搜/剩余，各来源产出，剩余 provider、输入 token 与 LinkedIn 额度。
- **由模型选择 LinkedIn 翻页深度。** `search_jobs.pages` 可选 1–8；不写时沿用原默认值。
- **停止理由。** 有搜索的回合，`finish_task` 需附一句 `stop_reason`（只做结构检查）。共用提示加入按预期价值决定继续或停止的说明，不设门槛。
- **最终回复内联信息。** 已保存推荐的内联列表带上类别、差距、待确认与下一步，写最终回复无需翻档案。
- **类别标签匹配。** 忽略标点与空格差异（例如 “Worth trying – known gaps”）。

### 7.2 本次完整验收的速度与 token 评价口径（测试前写定）

可比历史（同请求、同档、Jev、Treg 关闭）：

| 运行 | 正文读取 | provider | 输入 / 输出 | 总用时 | 首个结果 |
|---|---:|---:|---:|---:|---:|
| v2-01 | 24 | 38 | 376,291 / 53,884 | 344 s | 166 s |
| v2-02 | 24 | 30 | 225,313 / 39,896 | 211 s | 128 s |
| expanded-02 | 62 | 98 | 895,688 / 108,753 | 1,068 s | 597 s |

评价规则：
- **按工作量归一。** 每份已读正文输入 token ≤ 15.7k、provider ≤ 1.6 次、≤ 17 秒，与历史相当；高出 v2 两次中较差者 30% 以上（> 20.4k、> 2.1 次、> 22 秒）为需改进。
- **首个可用结果。** ≤ 200 秒为相当；> 260 秒为需改进。
- **总量。** 若模型因停止判断变化而多搜，总用时与 token 会随工作量增加；只按归一指标与产出判断，不因总量变大判退步，也不因未超预算判合理。
- **浪费。** 以下任一不为 0 即标为需改进：重复评分、重复详情读取、同一引用重复翻阅超过 2 次、对已保存岗位重复 `recommend_job`、被拒的 `finish_task`。

## 8. 验收版本 `tiered-recommendations-v4`（2026-10-14，用户同意）

依据 12.10 的测量：模型 20/20 选择停止，与事实和推理强度无关；同一输入的停止审计结论不一致。

- **停止。** 仍由模型决定。若仍有未覆盖的部分，回复必须照记录的数字写明，并给出可执行的继续方式（回复 “search more”）。`search_coverage` 给出每个 LinkedIn 查询的 `unseen`（来源总数减已返回卡片，纯算术），并保留之前回合的查询，供后续回合继续。
- **审计（同一次回复审计调用）。** 新增三项判断：用户是否明确要求尽量全面（`user_asked_exhaustive`）；仍有剩余时是否写明并给出继续方式（`continuation_stated`）；所写数字是否与记录一致（`continuation_accurate`）。
- **失败条件。**
  - 有剩余却未写明，或写得不准确：`continuation_missing_or_inaccurate`。
  - 用户要求尽量全面且停止明显过早：`search_stopped_prematurely`。
  - 其他情况下，停止合理性只作为改进建议。
- **后续回合。** 像 “search more” 这样的追问沿用对话中最近一次搜索的职位与地点。该回合实际做了搜索工作后，按搜索回合处理；与搜索无关的追问仍按普通问题处理。
- **不变。** 第 6 节的实质错误条件。
