# JobHunterAgent 优化收尾、统一迁移与 LinkedIn MCP 实施总纲

日期：2026-10-12。状态：R1 已执行，迁移准备门按[用户确认的修订](r1-r2-api-first-gate-amendment-20261012.md)允许进入 R2；旧 B6 业务失败保留。R2–R9 尚未据此宣称完成。

## 1. 文档关系与总目标

本总纲负责后续任务顺序、阶段依赖、来源策略与 LinkedIn MCP 接入验收。详细迁移按 [统一 Loop 迁移方案](unified-loop-migration-plan-20261012.md) M0–M7 执行；现有优化按 [P0–P9 优化主计划](integrated-optimization-execution-plan-20261012.md) 与最新诊断执行。阅读顺序为本总纲 → 对应阶段详细计划 → 最新诊断 → 实际代码。

相关交接：[optimization 交接](integrated-handoff-claude-to-codex-20261012.md)、[Treg A/B 计划](opt-v3-stage-1b-treg-ab.md)、[Treg 交接](treg-ab-execution-handoff-20261012.md)、[原真实验证计划](../diagnostics/integrated-live-validation-plan.md)。报告中的完成声明需与提交、日志和账本对应；不能仅凭交接文字判定通过。

总目标：一个通用 AgentLoop、一套逻辑执行所有权和恢复机制、多种来源能力。固定分析、材料和面试步骤作为业务工作流运行，不为统一架构增加 LLM 路由。LinkedIn MCP 是搜索/读取能力，不引入另一套决策循环。

后续来源组合：公开招聘板 API 为基础；Treg 补充发现和抓取；LinkedIn MCP 验收后承担 LinkedIn 专用搜索与读取；浏览器处理必要核验、特殊页面和投递。来源由配置、任务约束、健康状态与预算共同决定，不要求每次把所有渠道逐个尝试一遍。

## 3. 保留已有能力与边界

- 公开招聘板适配器是全用户可用的代码能力；具体接口是否公开、是否需 key 以各接口契约为准。公开岗位不依赖申请人账号，但通常需要 company/board 标识，不构成全市场搜索数据库。公司发现与 board 映射继续保留。
- 公共原始岗位数据与用户匹配结果分开。原始数据缓存按来源、board、岗位 ID、时间/版本组织；简历、匹配、面试和授权不能跨用户复用。账号会话来源默认按用户/会话隔离。
- Treg 保持开源用户自行配置 key、支持 `.env`、无统一托管收费；不修改用户现有 key。AnyAPI/Crawl4AI 以已有真实比较及最新结果决定，HarvestAPI 非必选。
- 继续排除 Adzuna、TheirStack；Agent Reach 整包、Boss、Jina 和新自主多 Agent planner 不进入本轮。可借鉴来源诊断模式，不批量增加无需求渠道。
- Pi/ai-job-search 的已采纳优化保留在现有实现和 P0–P9 验收中，不再作为独立重写项目启动。
- R1 必须检查最新真实验证状态。当前 `integrated-live-validation-plan.md` 已记录一次 L1 连接失败且 usage unknown；不能因为更早交接说已获授权就将其算通过或把费用算零。保留 B6 质量门槛、A5 user-deferred 和 fast 未配置等原状态，实施时按最新证据更新。

## 4. LinkedIn MCP 的实现依据与接入范围

审查源码快照：[`stickerdaniel/linkedin-mcp-server@5bdef1c93ff394386430faf81aed404a9e205fc7`](https://github.com/stickerdaniel/linkedin-mcp-server/tree/5bdef1c93ff394386430faf81aed404a9e205fc7)，其 pyproject 声明版本 4.27.0。此处是已阅读基准，不保证对应发行包已经发布；实施时核验可安装版本与源码一致性，固定验证过的版本/提交，禁止 `@latest` 静默升级。

主要依据：[工具定义](https://github.com/stickerdaniel/linkedin-mcp-server/blob/5bdef1c93ff394386430faf81aed404a9e205fc7/linkedin_mcp_server/tools/job.py)、[岗位读取/分页](https://github.com/stickerdaniel/linkedin-mcp-server/blob/5bdef1c93ff394386430faf81aed404a9e205fc7/linkedin_mcp_server/linkedin/jobs.py)、[登录配置](https://github.com/stickerdaniel/linkedin-mcp-server/blob/5bdef1c93ff394386430faf81aed404a9e205fc7/linkedin_mcp_server/config/loaders.py)、[依赖](https://github.com/stickerdaniel/linkedin-mcp-server/blob/5bdef1c93ff394386430faf81aed404a9e205fc7/pyproject.toml)。

该项目使用登录后的浏览器，以确定性代码完成搜索、翻页和正文提取。返回包含 `job_ids`、`sections`、`section_errors` 等字段，不是已经校验合格的岗位列表。预期收益是减少模型指挥浏览器的往返，真实成功率与速度须实测。

R7 首批业务白名单仅包括：

| 上游工具 | 内部用途 | 限制 |
|---|---|---|
| `search_jobs` | 发现候选和岗位 ID | 页面上限、结果上限、截止时间必传/受控 |
| `get_job_details` | 读取 JD 与岗位状态 | 缺正文、关闭、限流须显式保留 |
| `get_job_apply_url` | 识别 Easy Apply 或公司申请入口 | 只读取，不提交申请 |
| `search_companies` | 发现 LinkedIn 公司页 | 不视为已验证公司官网/招聘板映射 |
| `get_company_profile` | 公司信息和必要 jobs 部分 | 限定 sections，按需读取 |

`close_session` 如需使用，只作为受控生命周期能力，不加入模型业务工具表。发消息、连接请求、收件箱、个人资料等不在本轮业务范围，不能依靠 readOnlyHint 自动放行。

## 5. R7 实现任务包

### L0 接口与配置准备

复用项目现有 `agent_runtime/mcp/config.py`、`client.py`、`manager.py`、`adapter.py`，先确认迁移后真实调用路径。已有 `StdioMcpClient` 使用独立事件循环线程和持久连接；已有 allowlist、read_only_tools、超时与状态诊断，优先复用，不重写 MCP transport。

上游以独立环境/子进程运行，避免其 FastMCP、Python、Patchright 依赖挤入主服务环境。明确 Windows 安装、浏览器首次准备与正式调用的不同耗时。默认配置 disabled、required=false；未装 uv/浏览器或未登录不能阻止主应用启动。

产物：`docs/diagnostics/linkedin-mcp-contract.md`，记录固定版本、启动参数、环境兼容性、发现的工具 schema、错误样本、会话存储位置和生命周期。配置项名称以现有 loader 实际支持为准，不在 README 写未实现的变量。

现有运行配置的调用超时默认 30 秒、结果上限默认 20,000 bytes；文件配置暴露的字段与运行对象不完全相同。必须核对并测试：哪些限制可以配置、结果如何归档、超时是否取消底层工作。不得只把数值无限调大，或截断 JSON 后交模型猜测。

### L1 岗位来源适配

建议新增领域适配器（例如 `career/linkedin_source.py`），通过统一能力执行边界调用 MCP；注册到迁移后的来源选择与 JD 读取流程。模型看到稳定的岗位能力，不必额外加载上游全部工具 schema。具体文件名可调整，不改责任边界。

统一结果至少包含：source、source_job_id、canonical_url、title/company/location（可空）、retrieved_at、query/filter provenance、JD 状态、apply URL/type、partial/错误原因、原始证据引用。缺失字段保持未知，不让模型补造。原始响应有界归档；模型获得候选摘要和必要证据，不重复收到全文。

身份以 LinkedIn job ID 为主，规范化 URL 为辅；跨 Treg/浏览器同一 LinkedIn ID 合并。跨 ATS ID 仅在可信外部申请链接等证据明确时关联，不能仅靠公司名+职位名合并。

`section_errors`、MCP `isError`、调用超时与无匹配必须分别处理：无匹配不等于来源故障；丢失筛选条件不能当满足筛选；部分结果保留有效部分但不得声称完整；关闭/缺 JD 不能推荐为有效岗位。已有资格、推荐和来源校验继续执行。

### L2 会话、取消与健康状态

用户自行维护登录会话。固定版本支持的 `--no-auto-import` 用于关闭默认扫描本机浏览器；提供显式登录操作，用户自行完成登录。验证配置目录/profile 隔离和注销效果，日志与 `.env.example` 不写 Cookie/密码。不得通过更换账号/profile 绕过限流。

每个用户的 MCP 进程/会话有独立归属；同一会话第一版串行调用，复用连接和浏览器。不得与现有投递浏览器同时操控同一 profile。执行层记录 call ID、deadline、cancel、结果/unknown；外层超时不视为底层已停止，确认取消或受控回收后才能安排下一调用。

健康状态区分 disabled、未安装、配置未验证、待登录、ready、限流、暂时错误。状态检查使用缓存/按需探测，不在每个模型回合全量检查平台。登录失效、验证码、限流进入暂停/冷却或用户处理，不立即改用自主浏览器继续访问同账号同来源。

## 6. R7 测试方案与门槛

### T0 离线与本地假服务验收

禁止真实网络、收费模型和真实账号。测试以下契约：

- 正常候选、分页 ID 去重、跨来源合并；条件丢失、无匹配、部分结果、限流、登录失效、缺 JD、关闭岗位。
- 超大响应、非法 JSON/schema、超时后迟到结果、取消、进程退出、重启恢复、关闭连接；残留调用不得污染下一任务。
- allowlist 拒绝非业务工具；跨用户会话、证据与缓存隔离；未配置仍可走原招聘板 API。
- 执行预算和来源健康策略生效；新通道使用统一 Loop，不复活旧 Session；固定抓取步骤不新增 LLM。

新增有意义的适配器、调用生命周期及端到端来源回放测试，复用现有 MCP/搜索回归。产物 `docs/diagnostics/linkedin-mcp-offline-validation.md`；T0 未通过不得开始真实账号测试。

### T1 真实工具可用性测试，零模型调用

需要用户已选择的测试账号和可用登录会话，不能推断本机登录浏览器就是测试授权。冻结三组关键词/地区/筛选条件，由当前求职目标选取，不带简历敏感内容。每组一次 `search_jobs(max_pages=2)`，按固定顺序去重后最多五个岗位读取 JD，其中最多两个读取 apply URL。另做一次公司搜索、一次公司资料读取。

首次批次上限：3 次岗位搜索＋15 次详情＋6 次申请入口＋2 次公司查询＝26 次业务 MCP 调用；所有重试占用同一额度，不自动重开批次。默认每次工具 deadline 不超过 120 秒、整个批次 30 分钟，首装/人工登录单独记录且不混入 warm 耗时。具体数值是本计划建议的试验限制，不是已实测性能。

记录上游内部翻页/重试可观察信息；26 次 MCP 调用不等于 26 次网站请求。若出现登录挑战、限流、错误账号、数据串用或无法取消的调用，停止该来源，先修复/处理，不靠加调用数取得好结果。

T1 通过要求：三组搜索均获得可解释结果（真实无匹配可单列，但不能用于证明覆盖）；所有调用有完整成功/失败/partial 状态，零串号/重复执行；抽查详情与对应页面证据一致；apply URL 类型正确；冷启动与 warm 数据分开。样本不足以比较时结论为未决，不强行采用。

### T2 与现有方式对比

先以 T1 录制的脱敏内容做相同候选/详情的离线任务回放，验证新适配器不会增加主模型往返。真实 A/B 仅在 T0/T1 通过、执行授权与模型剩余预算明确后开展。

比较 A＝已验收的现有自主浏览器 LinkedIn 搜索，B＝专用 MCP 搜索；同账号、同查询、同候选上限、同模型/提示/资格标准。三组各一对，按 A/B、B/A、A/B 交替，记录市场变化和不同结果集。不得为了对比重启已被限流的来源，不在同一会话并发两条路线。

若现有 A 没有可重现的成功基线，记录“基线失败/无法比较”；允许证明 B 的可用性，但不能报告虚构的百分比加速。Treg 可引用已有证据，不默认增加第三个收费实验组。

真实 Agent 对比的建议硬上限为每次运行 20 个 provider attempts、100K 原始输入 token、15 分钟；六次合计 120 attempts、600K 输入。必须取这些上限与既有获准剩余额度的较小值；未核实预算前只准备运行器。输出按既有模型上限和实际 usage 记账，未知用量保留预留，不赋虚构美元价格。这些是规划上限，不是本文件新增的付费授权。

每条路线每组最多两页、五份 JD、两个 apply URL；T2 的 B 最多 24 次 MCP 业务调用，与 T1 分账，不无限追加补样。费用、重试和失败都计入结果。人工取证尽量使用已保存响应/页面，新增真实读取也需登记。

报告指标：有效唯一候选数、筛选符合率、JD 完整率、原文一致性、apply URL 有效率、主模型 attempts/input/output/cache、外部工具调用、总耗时、首次候选时间、登录介入次数、失败/partial/unknown、实际费用或未知费用。页面数/有效样本不足的情况单列。

### 采用标准

硬门槛：T0 全过；无身份/权限泄漏，无审批绕过，无把 partial 当完整或关闭岗位当有效；不绕开原资格标准；取消和失败恢复可用。

建议的“小样本默认采用”门槛：至少两组具有可比的非空结果；B 的合格候选覆盖不低于 A 的 90%，JD 完整率不低于 90% 且不低于 A；主模型 attempts 或原始输入中位数减少至少 20%，另一项不明显恶化；端到端 warm 耗时中位数增加不超过 10%。这些阈值须在测试前冻结，不得看完结果后降低。样本只支持当前条件下的采用决定，不宣称统计显著或长期稳定。

结论分三档：采用为已配置用户的 LinkedIn 默认来源；保留可选实验功能（可用但收益/覆盖未决）；延期关闭（硬门槛失败或质量不足）。没有达到默认门槛，也可保留只读可选能力，但报告必须明确原因。

产物：`linkedin-mcp-live-validation.md`、`linkedin-mcp-comparison.md`、脱敏原始结果/逐次账本与复现配置。每阶段报告单独标记通过、失败、未测。

## 7. 测试授权与计费继承

当前请求只授权修改文档。本轮不安装、不启动服务、不操作登录、不请求真实 LinkedIn/Treg/模型接口。

后续实施尊重会话内持续有效的授权：已明确批准的范围不重复询问。原 optimization 的 live lane 继续使用其原预算和批次账本；本计划不扩大其额度。LinkedIn 登录会话使用、真实 Agent A/B 和任何新增收费范围必须与已授权范围核对；缺少范围/额度时完成全部离线准备后，只询问缺失的具体事项。

Treg 交接曾报告 15 次调用、$0.004、0 unknown、0 LLM，执行前以最新账本为准。不得重置旧 A/B batch，不把 Treg 费用额度用于模型，不为了验证 MCP 再重复收费爬取同一批数据。上游开源工具本身不等于端到端零成本，模型、环境和维护分别记录。

## 8. R8 默认策略与回滚

通过验收且用户配置可用时，LinkedIn 搜索首选专用 MCP。未配置则继续已有已验收策略；招聘板与 Treg 的启用、价格预算及数据范围保持独立，不因启用 MCP 自动关闭全部 Treg。

MCP 返回完整可靠结果时不再打开浏览器重复核验同一内容。缺 JD/申请链接或有证据冲突时，按任务需要补读；登录失效、验证码、限流不触发同账号浏览器自动绕行。公司官网投递继续由现有 ApplicationHost 与审批机制负责。

回滚只关闭 LinkedIn 来源开关、停止安排新调用并处理在途调用。保留已有候选及来源证据，不删除登录文件、不重新执行未知调用、不切回已删除的旧 Agent 循环。依赖升级作为单独变更重跑契约与最小真实验收，不跟随每次启动自动更新。

## 9. R9 开源交付与最终检查

README 写明基础招聘板无需 LinkedIn 会话、Treg 自带 key、LinkedIn 自带登录；支持的平台/环境、固定版本安装、显式登录、关闭自动导入、启停/注销/清理方式、限流和失败提示、来源选择及测试证据。`.env.example` 只放实际实现的开关和占位值，不存 Cookie，不承诺仅填 env 就能完成浏览器登录。

MCP 示例配置必须匹配项目 loader，使用 args 列表、业务 allowlist、required=false、受控超时；工具命令来自可信配置，不允许岗位页面内容改变启动命令。用户界面展示可理解状态，不要求用户理解 MCP 内部字段。

R6 的 API 优先 B6 必须使用原合成候选人和业务断言，移除强制 browser-first 的测试指令；R8 若改变已验收配置，R9 补受影响验证，配置未变则引用原证据。不能为测试 MCP 强制增加未验证来源，不能因新 API 路线仍失败而宣称最终完成。预算与运行器细则见门槛修订。

最终报告 `docs/diagnostics/execution-roadmap-final.md` 汇总 R1–R9、优化/迁移/来源各自状态、已采用默认值、可选能力、失败/未测项、剩余成本与运行限制。基本安装流程分别验证：无额外凭据、只配置 Treg、只配置 LinkedIn、两者均配置。

## 10. Codex 执行入口

从 R1 开始检查当前仓库和最新诊断，输出已完成、待验收、阻塞及原始证据位置。依据事实跳过已经完成且未受改动影响的工作，不重复开发或收费测试。R1 完成后依次按迁移 M1–M7 推进 R2–R5，再完成 R6 和 LinkedIn R7。

每阶段小范围提交代码、必要回归与诊断；保留其他会话改动，不改资格/推荐评估标准，不修改密钥，不推送部署或迁移真实数据库，除非另有对应授权。诊断文件名在实施阶段创建，不提前创建空的“通过报告”。

总完成条件：唯一生产决策内核与逻辑执行控制层；历史读兼容；原来源链路不退化；LinkedIn 有明确采用决定且默认行为匹配证据；付费/登录边界清楚；README 与真实配置一致。任何旧循环仍可作为生产 fallback，或仅配置 MCP 却未接到主搜索链路，都不算完成。
