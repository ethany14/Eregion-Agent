## 2.1 开源用户自带 Treg key 的接入方式

推荐 **Python 后端直接调用 HTTP API**。Treg 官网的主流 agent 安装按钮是现成客户端配置入口；官方同时支持普通 HTTP（无需 SDK）、MCP 和 CLI，因此自研 agent 不需要等待官方适配。

连接路径：`用户自己的 .env / 进程环境 → 用户自己的 Python 后端 → 原有 search_jobs/read_job → TregJobsAdapter → Treg HTTP → 显式选定的 AnyAPI / Crawl4AI → 统一岗位证据 → 原资格校验/导入/评分`。密钥只由后端配置层交给 HTTP 客户端，不进入模型上下文、浏览器、前端构建或工具返回。

实施与配置步骤：

1. 每个使用者在自己的 Treg 账户创建/选择团队并获取 API key，自行写入自己项目根 `.env` 的 `TREG_TOKEN`，也可通过进程环境变量提供。仓库只提供空值示例，项目作者不提供公共 key；该 key 与 `LLM_API_KEY` 分开。
2. 组织限定 dashboard key 发送 `X-Treg-Token` 即可；使用 identity token 时再发送 `X-Treg-Org`。支持范围内可使用 Treg 的上游凭据，不必另建 AnyAPI/Crawl4AI 账户；实际可用性和费用以该账户 access/price 信息为准。
3. 在 `treg_client.py` 用项目已有的 `httpx` 发送 `https://treg.to/call/<端点ID>`，HTTP method、参数和返回解析按 A1 确认。发送费用上限及幂等 header，采集 call ID 和费用；客户端不是给模型执行任意 URL 的代理。
4. 在 `treg_jobs.py` 包装岗位搜索与按需正文提取能力，harness 仍暴露原业务工具。模型选 `search_jobs` 后，由后端依据来源政策调用适配器，不要求模型记住 Treg 认证或 API 参数。
5. 原 optimization 收尾后，完成 A+B 离线门，再在隔离测试配置中启用真实 API 冒烟。测试结束关闭该测试开关，发布默认仍关闭。使用者自行启用 `JOB_AGENT_TREG_ENABLED` 后，费用计入其自己的 Treg 账户；未配置 key 仍可使用已有招聘板 API 与浏览器。

不需要安装 CLI 才能发送 HTTP，不需要向 Treg 注册/上传整个 JobHunterAgent。若未来项目已有通用 MCP client，也可使用 `https://treg.to/mcp/`；此次使用显式端点白名单直接 HTTP 更容易复用现有预算、缓存和业务校验。Treg 是外部工具网关，与模型调用网关属于不同接入层。

## 3. A：接入基础设施

### A1. 固定端点与契约

本轮仅允许以下三个候选端点；均先核实契约，不预先承诺全部进入正式默认路由：

| 端点 | 用途 | 禁止推断 |
|---|---|---|
| `anyapi.linkedin.search.jobs` | LinkedIn Jobs Index：标题、公司、地点、日期和链接 | 不含完整 JD；不得自动升级到收费更高的 `.full` |
| `crawl4ai.linkedin.search.jobs` | LinkedIn 公开岗位搜索 | 返回链接/卡片不等于完整 JD、仍在招或符合资格 |
| `crawl4ai.web.scrape` | 对已初筛候选的公开岗位 URL 提取正文 | 成功响应不代表正文完整；登录页、验证码、列表页及空正文不得充当 JD |

不纳入本轮：HarvestAPI 搜索/详情、AnyAPI full、Crawl4AI LLM structured extract、整站 crawl、公司页面发现、其他网站 Recipes、自动充值或提额工具。公司招聘页发现可留待第二轮另定范围与预算。Treg 中的 Crawl4AI 云端能力不等同于安装开源 Python 库；本期不新增自部署爬虫。

网关固定为 `https://treg.to/call/<endpoint>`。按官方契约使用 `X-Treg-Token`；优先组织限定令牌，确需 `X-Treg-Org` 时只能由后端配置。模型输入、网页文本和工具返回不能改变网关、端点或认证信息。不支持任意代理、跳转跟随、自定义外部主机；轮询 URL 必须同样校验，不能转发凭据到其他 origin。

实施前，从公开权威定义确认并记录：HTTP method、query/body 参数、岗位 ID 类型、地点参数、分页游标、响应 envelope、空结果、错误与异步状态、计费与幂等字段。不能把示例或目录摘要当成完整契约。若地点需要 geo ID，先确认可以由现有参数表达；不能猜测 ID，也不能悄悄添加 `geo.search`。无法支持的筛选项必须明确返回「未应用/需证据核验」，不得伪称已过滤。

交付 `docs/diagnostics/treg-ab-contract.md`：逐端点列公开定义链接、获取日期、采用的契约版本/摘要哈希、字段映射和未确认项。fixtures 区分 `synthetic`、官方示例和脱敏真实录制；合成数据不能写成实测。公开输入契约、认证、价格界限明确后，可以在第 6.1 节的小额 API 通道核实真实响应并更新记录。没有明确的请求构造或费用上界时，标为 `unverified` 并阻止启用，不能通过无界试错猜参数或编造格式。

每个请求显式绑定上述端点及 provider；对比测试由固定脚本分别调用两家，不启用 overflow、自动择优或动态路由。正式接入按第 6.1 节证据选一个默认搜索源，另一个仅作可配置备选，不在每次搜索中双调用。若 Crawl4AI 上游有备用数据源，须记录其来源披露与计费规则；显式端点并不保证其内部从不切源。若账户或响应可能替换 provider，需在契约中确认禁用办法；未确认时不能声称固定成本或固定来源。响应出现意外 provider 要记账、隔离结果并报告，不能静默接受。

### A2. HTTP 客户端、期限与生命周期

- 复用项目已有 HTTP 设计和公共 URL 校验；Treg 认证客户端与普通岗位抓取凭据隔离。`trust_env=False`、禁用自动重定向，明确注入与关闭责任。
- 默认读取超时建议 20 秒，连接/读写超时和整项操作 deadline 分别限制；单次请求超时不能替代整体期限。
- 默认每个进程最多 2 个并发 Treg 请求；任务及本部署日预算的并发竞争仍须靠持久化原子预留控制，不能声称本地信号量覆盖多进程。
- 网络错误和可恢复 429/5xx 最多追加 1 次受控重试，遵循 deadline 与 `Retry-After`。SDK/传输层自动重试关闭，避免多层叠加。超时、取消后的收费不确定性按 A4 处理，不直接重发。
- 400/401/403/404/422 默认不可重试；解析、权限或配置失败给出结构化原因，不将错误当成空搜索结果。
- 所有对外请求通过一个可替换传输入口；日志、异常、诊断文件不包含认证 header、令牌或个人简历。

### A3. 本部署的消费记录与预算（非托管计费）

新增外部工具调用记录，建议模块 `agent_runtime/career/external_tool_usage.py`；最终名称可按仓库惯例调整。采用使用者自己部署的现有数据库和迁移机制，不新建旁路 JSON 计费系统。只记录本部署发起的操作、上游费用和预算占用，用于防重复调用、控制支出和故障恢复；不建设 customer/workspace 分账、用户扣款接口、收费套餐或作者侧消费汇总。

至少区分：

| 对象 | 必要信息 |
|---|---|
| 逻辑操作 | operation ID、task/run、用户目标 revision、预算 scope、endpoint、provider、规范化请求哈希、幂等键、状态、创建/更新时间 |
| 网络尝试 | operation ID、attempt ID、阶段（执行/轮询/查询）、起止时间、HTTP/错误分类、可恢复性、Treg call ID |
| 费用事实 | 预留上限、已确认实扣、尚未确认的占用、币种、计费日、原始费用来源、是否重放、对账状态 |
| 结果关联 | candidate identity、证据引用/哈希、结果是否因取消或 revision 变化而丢弃；不在计费表复制整份正文 |

金额用整数 micro-USD；配置金额通过 Decimal 严格解析，拒绝负值、NaN、超精度等，不使用浮点累加。幂等键相同或相同 Treg call ID 的重复回包不得重复计费；每次网络尝试仍保留记录。未知费用不得当成 0。

发送前，在短数据库事务中原子检查并预留 **任务累计上限 + 本部署 UTC 日累计上限 + 请求次数上限**，成功后才允许发网络请求。不在数据库事务内等待网络。进程重启、新用户轮次、换 query、换工具、失败重试均不得清空任务已花费；本部署日预算覆盖共享该数据库的多个任务/worker，不能依靠每个 service 对象的内存计数。

本期一个部署配置一个 Treg key，不实现多账户管理。预算 scope 使用持久化的本部署标识，不把原始 token 当数据库键、日志字段或报表内容；更换/轮换 token 不清空本部署已花费和未决占用。独立部署或其他应用使用同一 Treg 账户产生的支出不在本地账本内，不能宣称此限额限制了整个 Treg 账户；不为此引入中心计费服务。

同一操作只做一次费用预留；重试增加 attempt 计数，需要额外可能收费的操作必须重新预留。任务取消、结果不可用、评分失败或最终无推荐，已经发生的工具费用仍计入任务总成本。日期跨越时保留原预留所属的计费桶，不能凭本地午夜释放未决费用；实际结算日期/规则如有差异要记录并报告。

每个端点必须有已验证的单次最大费用界限或官方支持的收费上限机制，才能允许启用。公开单价仅用于配置参考，不能当成未来不变的价格承诺。按当前官方协议，`X-Treg-Route-Max-Cost` 也适用于 direct `/call/` 请求，超过预留界限会返回 402；在真实验证前再次核对，固定端点每次调用也必须发送。此单次保护**不能代替本地累计预算，也不能单独证明账户硬限额**。不能确定费用上界时拒绝调用。出现实扣超过预留时记录真实超额、停止后续调用并报告，不截断账本数值。

扩展现有 usage/report：分别显示模型已确认费用、工具已确认费用、工具未决占用、总已确认费用及总费用是否完整。Treg 返回的 `X-Treg-Call-Id`、`X-Treg-Cost-Micro`、幂等重放与原调用费用字段按已确认契约处理，不能将「原始费用」和「本次重放费用」相加。

### A4. 幂等、异步、取消与恢复

- 幂等键在发送前持久化；同一逻辑操作重试保持原键。幂等有效期采用官方当前契约，不无限假设有效。
- 请求指纹包含 endpoint、provider、规范化参数、分页游标及用户搜索目标 revision；只在适当范围复用，显式刷新必须形成新的受预算控制的操作。不要永久缓存相同 query，也不要把换一个无意义参数视为新进展。
- 状态至少能表达：reserved、in-flight、pending、succeeded、failed、unknown、cancelled；费用确认状态独立，`failed/cancelled` 不自动代表退款或无需对账。
- 202 或官方定义的 pending/409：保存原 operation/回执，按已确认协议有界轮询或取回，不能另起收费任务。轮询也是网络尝试；只有官方确认其免费，才能不预留额外费用。
- 410、过期回执、超时、连接中断、进程在发送后崩溃、费用字段缺失：保守标为 unknown，保留费用占用和可恢复标识。先查询原操作；无法确认是否执行时，停止该操作并报告，禁止换新幂等键盲目重发。
- 重启必须能识别已预留未发送、已发送未收到、已成功未提交本地业务结果等窗口；多个 worker 恢复同一操作需持久 claim/租约或等价互斥，不能重复启动。claim 失效不能证明上游未执行。
- 取消后停止新请求与新轮询。迟到结果只能按必要程度完成计费和证据记录，不能推进已取消或旧 revision 的任务；恢复旧结果必须验证当前目标兼容性。
- 关闭功能开关后不得启动后台收费对账。保留未决记录；崩溃、重试风暴和并发恢复优先用模拟服务验证。真实测试中产生的未决记录可在该批次剩余预算/次数内查询，不发新收费操作替代旧操作。

## 4. B：API 优先的岗位搜索与 LinkedIn 接入

### B0. 目标流程：API 优先、浏览器补充核验

本节定义 `JOB_AGENT_JOB_API_FIRST=1` 时的业务流程，沿用原 optimization 收尾后的任务推进机制；不在本任务额外重建阶段 4 工作流或增加通用批量执行工具。

`用户搜索条件 → 来源内 API 批量检索 → 身份去重与确定性初筛 → 复用完整正文/按需补齐详情 → 资格校验 → 导入 → 评分 → 推荐`

浏览器是这条链路的按需分支，不是每条岗位必经的一步：

1. **确定搜索目标一次，按目标 revision 保存。** 记录职位方向、地点、远程、年限、发布时间和来源限制；用户变更目标才相应更新。不得为同一批岗位反复改写 query 触发重复检索。
2. **在允许的来源中优先调用 API。** 已知公司/招聘板用已有 API；未限定来源时先用可信招聘板目录，不要求先打开浏览器或等待阻断。目录无覆盖或候选不足，再在 Treg 已启用且有预算时补充 LinkedIn。明确只查 LinkedIn 则直接走配置中选定且可用的搜索适配器，不先遍历其他招聘板。不是对所有来源无差别并发搜索。
3. **批量获取、代码初筛。** 在现有候选数、页数、deadline 和来源限流内合并结果；只根据有证据的地点、岗位类型等排除确定不符的条目。身份去重优先于新增详情调用与评分；未知年限/签证/岗位状态不能当作满足，也不能仅因缺字段就伪称不符合。
4. **正文复用，详情按需。** 搜索或已缓存结果已含同一岗位、足够新且完整的正文时直接复用；未完整时按已有招聘板 API → 已验证并启用的 Crawl4AI 正文抓取 → 浏览器补充的顺序获取；不强制购买岗位详情接口。仅对初筛后的候选补齐，不批量打开全部搜索结果。可复用现有有界并发机制补齐独立候选，遵守每来源限流、Treg 并发和原子预算；取消、目标变化或配额耗尽后停止新请求。不让模型为每个候选反复发出“打开页面”的机械指令，也不将所有原始 JSON/正文一次塞进模型上下文。
5. **明确浏览器触发条件。** 用户显式要求页面/区域观察；API 缺少必要证据且已有详情/缓存无法补足；证据冲突、时效不足或岗位有效性存疑需要原页面核验；或该来源没有可用 API 且确有待解决的信息缺口。每次记录具体核验原因与目标岗位。API 失败不等于必须打开所有候选页面，已有浏览器阻断和无进展保护继续生效。
6. **证据足够就不重复浏览。** 没有上述触发条件时，完整可靠 API 证据可以直接进入原资格/导入/评分路径；不得仅为“看过网页”重复打开每个岗位。若必要核验无法完成，标记待核验或不推荐，不冒充已确认。已进入申请流程所需的浏览器操作沿用原实现，本任务不修改投递行为。
7. **批次之间按缺口推进。** 先处理可行动候选，再按合格推荐缺口决定补搜或下一页；达到目标或预算就停止。取得若干链接不能代替达到合格推荐目标。

同步调整启用状态下的 `search_jobs` / `read_job` 工具说明、提示和路由判断：不再引导“先浏览器，受阻才使用目录”或“只要页面打开过就必须浏览器读”。遵守阶段 2 工具稳定性：同一配置/任务内定义保持稳定，不依据某次是否阻断随意改变工具列表。两个开关都关闭时保留旧定义以便回滚。

### B1. 统一候选与证据

适配器输出现有领域对象，不让 harness 依赖 provider 原始 JSON。保留以下语义，优先复用已有字段，必要时增加明确的内部元数据：

- `job_key`、canonical URL、原始 URL、provider job ID、source endpoint/provider；没有稳定身份的条目不得猜 ID 或按数组索引生成持久身份。
- 标题、公司、地点、remote 等有来源的事实；缺失字段保持未知，不按查询条件补齐。
- `fetched_at`、provider 提供的发布时间及其精度/时区、首次观察时间分别保存；首次抓取不能冒充新发布，缺少发布时间不能通过严格 freshness 条件。
- 正文、摘要、完整性状态、原始响应版本/证据引用与哈希。完整性未知时保守处理；搜索摘要不能进入「完整 JD」缓存。
- 结构化 seniority、employment type、active 状态属于 provider 线索；保留资格校验需要的原文，不能直接据此宣称满足初级/年限/有效岗位要求。

同一 LinkedIn job ID 的 URL 变体统一为一个岗位；跨平台去重只有在明确交叉链接或可靠标识证明同一 posting 时才合并，不能只按公司与标题合并不同岗位。换 provider 得到同一候选不是新进展；获得此前缺失的完整正文可以是新增证据，但不能清除已成立的资格拒绝记录。

### B2. `search_jobs` 路由与不足判断

1. 用户明确指定公司、招聘板或来源限制时遵守其范围；「只查 LinkedIn」不能偷偷换为其他来源。Treg 不可用或禁用时按现有行为处理并披露限制。
2. 用户指定 LinkedIn，且开关、契约、预算均可用时，调用配置中选定的 AnyAPI Index 或 Crawl4AI 搜索，不能每次同时调用两家。响应中明确标注实际 Treg 端点和 provider，不能冒充浏览器实查或官网发布。
3. API 优先开启且用户未限制来源时，直接使用可信招聘板目录 API，不以浏览器尝试/阻断为前置条件。现有任务评估确认「可继续推进的候选不足」后，最多启动受预算约束的 LinkedIn 补充搜索；不要在每次工具调用自动触发。
4. 「不足」依据去重后、未被资格拒绝/失效/永久失败的候选及当前目标缺口；没有核验的候选只算待处理，不能当作已合格。先推进已有候选，失败再补充，不能因为返回两条链接就宣告完成。
5. 搜索缓存键纳入 provider、来源范围、过滤条件、目标 revision 和游标。沿用无进展规则；相同页、重复游标、改写 query 返回同一批岗位都不能无限收费或推进进度。
6. provider 不支持的地点、发布时间、remote、seniority 条件标记未应用，在资格阶段以证据验证；严格条件缺少证据时不得推荐为符合。

### B3. `read_job` 与浏览器来源健康

用户明确要求当前浏览器区域/页面观察或传入 `region_ref` 时，保留原浏览器行为与身份核验，不以缓存替代这次显式观察。其余请求先检查同一岗位、与当前要求兼容、足够新且完整的证据缓存；缓存不足时，已支持 ATS 优先走现有 API 读取路径；其他公开岗位 URL 可进入已验证并启用的 Crawl4AI 正文抓取。只有 ID 时先依据确认的契约取得对应 URL，不能猜身份；取得可靠官网交叉链接时优先读取官网。浏览器仅按 B0 的条件补充核验，不能仅因 URL 已打开而改变读取优先级。以上新优先级在 API 优先开关开启时适用。

当前 `read_job` 的「同一 URL 已在浏览器观察过」分支，以及工具外层 `browser_preflight` 都要审查。**仅仅打开过同一 URL，不应强制后续详情读取回到浏览器，无论浏览器当前是否被阻断；但显式页面观察不能被 API 回包替代。** 路由须先确定本次传输，再执行对应健康检查。

分开记录：

- 传输健康：例如 `browser:linkedin`、`api:treg:anyapi:search`、`api:treg:crawl4ai:search`、`api:treg:crawl4ai:scrape`，以及错误作用域（全局认证/网关、端点、单岗位）。浏览器被阻断不能直接判 API 不健康；单岗位 404 不能封禁整个 provider；Treg 认证失败也不能污染普通 ATS。
- 共享业务证据：规范化 job identity、已读正文、资格拒绝、重复候选、无进展记录。不能通过换传输重新推荐已被拒绝的同一岗位。

保留 CAPTCHA、登录和浏览器阻断的原始状态；API 数据获取不是浏览器阻断已解除。最终回答准确披露读取来源与未核验部分，不实现绕过验证码或会话保护。

### B4. 业务链与阶段 2 兼容

向 `crawl4ai.web.scrape` 提交的 URL 也必须经过现有公共 URL/来源校验；拒绝内网、本机地址及携带凭据的 URL，不向上游传浏览器会话或简历。网页中的链接不能改变端点白名单，官网跳转需重新校验来源及岗位身份。

岗位正文进入现有 `posting_qualification`、`search_policy.opening_level` 和 import/score 路径，不新增「provider 返回即推荐」捷径。人才库、通用职位页、关闭岗位、Associate 缺少 junior 证据等继续按现有规则处理。

引用缓存、快照裁剪与稳定工具组遵守阶段 2 已有实现。正文引用必须在恢复后可取回，证据可用性不得仅依赖 client 内存；账本不是正文存储。此次不改变模型路由、推理配置、评分/简历缓存签名语义。

## 6. 离线验收：必须覆盖的失败边界

所有默认离线测试禁止真实网络、DNS、凭据读取和模型 provider；使用假令牌、HTTP mock transport、临时 SQLite/仓库测试 DB 和脚本模型。网络禁用要能拦截遗漏的传输路径，不能只 mock 一个成功调用。不能凭「没有配 key」声称零网络。显式 live 测试保持关闭，不因环境中已有凭据自动启用。

| 测试组 | 必须证明 |
|---|---|
| 默认兼容 | 两开关均禁用时旧路径、工具 schema 和模型请求不变；四种开关组合均有测试；Treg 关闭始终没有 Treg 网络/账务副作用，API 优先仍可独立用于招聘板；缺 token 也能跑旧路径 |
| API 优先 | 无浏览器历史且未发生阻断时直接调用招聘板 API；明确 LinkedIn 且 Treg 可用时直接走适配器；已有完整证据不重复详情读取、不打开浏览器；API 不足按缺口补搜而非遍历全部来源 |
| 浏览器补充 | 显式页面观察、必要字段缺失、证据冲突/过期、来源无可用 API 分别触发有原因的核验；完整证据场景浏览器调用为 0；核验失败不伪造完成；已打开 URL 在浏览器健康时也不强制重读 |
| 批量与范围 | 去重后才补详情，受控并发可取消，达到目标/预算停止；不增加 Adzuna 或 TheirStack 适配器、配置和请求；不把批量返回的摘要当完整正文 |
| 自配 key / 配置 | 临时 `.env` 单独配置可用；改变 cwd 仍取项目根配置；进程环境覆盖文件，显式空 token 不回退；无文件/无 key/占位值与非法预算处理明确；未启用时不消费，不访问维护者真实配置 |
| 开源交付 | `.env.example` 无真实密钥、默认禁用且不会自动跑 smoke；真实 `.env` 被忽略、示例可提交；README 保留用户已有配置；配置响应和日志不回传 token；无作者公共 key、统一代理或用户扣款路径 |
| 契约与映射 | 空结果、缺 ID/字段、分页重复、非法 URL、多岗位/错岗位详情、摘要/残缺正文、未知 active/发布时间、未应用筛选、未知字段；错误响应不是空成功 |
| 网络与错误 | 400/401/403/404/422 不盲重试；429/5xx 有界重试；超时/断连未知费用；2xx 缺费用、202、409、410 按契约分类；凭据不随跳转泄露 |
| 费用与并发 | 相同 call ID/幂等重放只记一次实扣；重试仍占 attempt；最后一笔余额的并发竞争只能有允许的调用发出；本部署跨任务 cap、新轮次/重启/跨日/token 轮换不错误释放；超额如实记录并停止 |
| 恢复与取消 | 各崩溃窗口可恢复；双 worker 不重复启动；取消/旧 revision 迟到结果不推进任务但费用保留；关闭开关不触发对账；unknown 不清零也不盲重发 |
| 来源治理 | LinkedIn 浏览器阻断、API 健康时允许适配器读；显式区域读取仍走浏览器；单岗位失败不封整个来源；资格拒绝/去重跨 provider 共享；同一 URL 已打开不导致错误强制浏览器 |
| 预算终止 | 达到费用、attempt、分页或整体 deadline 后可解释地停止；不通过换 query/工具/页码继续收费；provider 不可用不虚报成功 |
| 业务正例 | 新候选适配器 路径通过真实 CareerService/TaskHost/harness 与临时 DB，取得完整证据、资格验证、导入、模拟评分、最终推荐；不变的 `evaluate_search` 判定 ≥2 个合格推荐 |
| 业务反例 | 只有 1 个合格岗位、全部不合格、候选充足但证据不足/过期、明确来源限制等场景如实报告不足；不得补写证据或降低阈值凑足两条 |

保留 `tests/test_b6_offline_replay.py` 原有冻结回放与评价规则；新增 AnyAPI/Crawl4AI 场景放独立 fixtures/测试，不能用新合成数据改写旧基线。既有 fixture 中的合成标识也必须保留。模拟评分只验证链路，不构成评分准确率或真实模型质量证据。

至少执行：新增协议/账本/并发/恢复测试、来源和 posting qualification 回归、原 B6 离线回放、新候选适配器 业务回放、受影响的 usage/report 与阶段 2 稳定工具测试。按当前仓库实际测试文件固定集合、记录完整命令和版本；确认无网络后执行。新测试通过后不反复扩大无关测试。

新增同一离线候选集的旧/新路由对照，记录浏览器工具调用数、详情 API 调用数、重复读取数、模型往返数、合格推荐数及核验原因；完整 API 证据场景应做到浏览器调用为 0，必要核验场景必须保留浏览器分支。真实耗时和成本只用相应真实运行证据，不从 mock 延迟推算加速倍数；本任务不承诺固定百分比的性能提升。

验收标准为**固定版本与集合无新增失败**，不是某个固定 passed 总数。失败必须定位；不能把所有失败归为沙箱 named-pipe 问题。环境原因应提供同一测试在基线的证据，每个 skip 给原因。

### 6.1 AnyAPI 与 Crawl4AI 小样本对比：optimization 完成后执行

用户已明确接受本节测试范围与付费预算，无需重复请求同范围授权。**当前只更新文档，不执行测试或接入；先完成原 optimization，锁定基线，再完成契约核实、A 的费用保护及候选适配器离线门，之后进行对比，最后按结果确定 B 的默认接入。** 此对比是 A+B 内的小额验证，不是延期 D 的大规模/真实模型效果实验。

#### 预算和停止条件

- 两家搜索与正文抓取共用一个持久批次：**总上限 $0.10、最多 20 次网关请求尝试、每次 `/call/` 上限 $0.01**，任一先到即停止。两家分别拿 $0.10、重启/换查询/跨日重新计额均禁止；任务与本部署日预算同时适用。
- 实扣与 unknown 预留共同占用预算。重试、分页、轮询、状态查询也计次数和可能费用；预先核实分页/结果数对应最大扣费，目录中按结果与按请求的歧义未解决时不得调用。
- 计划 10 次搜索 + 5 次正文抓取；其余最多 5 次也必须容纳账户、access/price 预检、收据查询和必要的受控重试。预检如已用 5 次，则没有额外重试额度；必要查询更多时减少样本并披露，或停止，不能另开批次绕过 20 次上限。不得为用完余额扩充样本。报价超单次上限、累计预算不足、来源/计费异常即停，不自动换端点、升级 full、充值或提高额度。
- 真实入口显式 opt-in（如 `JOB_AGENT_TREG_LIVE_API_TEST=1`），普通回归零网络。统一配置加载器读取使用者自己的 `.env`/环境变量；隔离数据库、脱敏日志，不启用真实模型、评分或 verifier。真实 LLM 调用数必须为 0。

#### 固定样本和执行方法

1. 测试前冻结 **5 组职位、地区和发布时间条件**，覆盖目标求职范围中的不同职位表达和地点/远程条件；不携带简历或个人信息。记录完整查询表，两家使用语义一致的输入，交替执行先后次序以减少顺序偏差。
2. 每组 AnyAPI Index 与 Crawl4AI LinkedIn 搜索各 1 次，共 10 次；目标每家每组最多 10 条、首轮不翻页。参数无法等价映射时记录未应用条件，不能假装已过滤；必须付费增加辅助查询才能构造输入时，先调整为已验证支持的共同条件，不猜 ID。
3. 保留各家原始计数、去重计数、交集、独有岗位、URL、发布时间、查询匹配证据、响应耗时、错误与实际费用。依据已冻结规则核对标题/地点/时间匹配，未知字段单列。索引没有 JD 是预期行为，不算搜索失败。
4. 从两家合并去重、初筛通过的候选中，用固定规则选 **5 个不同的公开岗位 URL**，尽可能覆盖交集、两家独有结果及不同目标网站；不足 5 个则全部选取并披露，不额外补搜凑数。使用 `crawl4ai.web.scrape` 各抓 1 次；同一页面不按搜索来源重复付费。此阶段专门测抓取能力，正式业务路由仍优先已有 ATS API。
5. 检查正文是否属于同一岗位、是否含职责/任职要求/地点、是否截断，以及开放/关闭/无法确认状态。页面原本未披露的信息保持未知；不能因没有薪资或签证说明直接判抓取失败。登录页、验证码、列表页、摘要、失效页均不能算完整 JD。
6. 用返回正文和隔离保存的证据离线核对；本批次不为人工核验另外启动收费浏览器/LLM服务或扩展外部抓取。仍需浏览器核验的岗位标记待核验，后续正式业务流程保留该分支。失效比例只在有核验依据的子样本上计算，未核验不能算有效。

#### 对比指标与选型规则

- 搜索：可判断样本中的相关比例、去重后相关候选数、独有有效候选、筛选条件遵守情况、日期缺失、错误/空结果及每组响应耗时；列原始分子/分母，不把 5 组查询外推成全站召回率或稳定性保证。
- 正文：5 个抽样中的成功取得完整 JD 数、身份一致性、失效/阻断/未知数、抓取耗时及费用；保留原文以排查清洗遗漏，不能只凭 HTTP 200 判成功。
- 成本：分别列搜索费、正文费、失败/重试费、unknown 占用；报告**每个去重、有效且取得完整 JD 的岗位成本**及完整计算口径。当前只抓 5 条，端到端指标仅适用于此抽样流程，不能用全部未核验搜索结果作分母。共享岗位的正文费在两家假设流程中分别计入但批次账本只扣实际一次；预算不完整/分母为 0 时报告不可比较，不虚报零成本。
- Crawl4AI 搜索质量相当且正文提取合格时，可优先单一供应商以减少维护；AnyAPI 搜索明显更好时，选择 AnyAPI Index 搜索 + 已有 ATS API/Crawl4AI 按需正文提取。质量优先于目录价格，记录逐查询依据，不预设赢家。证据不足则保持新接入关闭或仅标为实验性候选，不追加未授权批次。
- 正式运行选一个默认搜索 provider，另一家仅为显式可配置备选；无自动双搜、付费详情购买或动态故障转移。Crawl4AI 正文抓取独立验收，搜索胜出不代表正文能力自动通过。README/`.env.example` 记录选定 provider 配置与默认关闭状态，模型不能更改 provider、凭据或额度。

#### 交付证据

输出 `docs/diagnostics/treg-provider-comparison.md`：基线版本、冻结查询、时间、契约来源、请求/样本计数、脱敏参数、call IDs、逐组结果、5 条正文检查、实扣/未决占用、选择及不确定性。此报告取代原仅验证 Harvest 搜索/详情连通性的 smoke 报告；只在允许留存时保存脱敏 fixtures。实际未执行的项目写未执行，不预填成功。

缺令牌/余额或契约不明时交付离线结果并注明阻断；不索取聊天明文 key、不假称实测，也不把缺配置写成缺授权。本会话许可不等于其他开源用户允许自动消费，发布开关和真实测试仍默认关闭。扩大样本、公司页面发现、其他来源或真实模型全链路需要另定范围与预算。
