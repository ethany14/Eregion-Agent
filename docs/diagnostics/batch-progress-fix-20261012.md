# 批量搜索推进修复与第二轮真实验收

日期：2026-10-12。第一组修复版本：`6c58fd1`，位于本地 main。

## 结论

流程已从“反复搜索读取、完全不评分”推进到真实评分，但 **10–15 个合格推荐的业务门仍未通过**。第二轮停止原因是完整 provider 调用预算耗尽，不是 MCP 抓取失败。不能用 3 条已保存推荐代替 10 条符合原条件的推荐。

## 已实现

- API 优先路线在未显式设置开关时，默认提供已有 verify_and_score 组合工具和候选队列；环境变量显式 0 可回退。组合工具继续调用原有处理器，唯一 AgentLoop/执行 owner 不变。
- 候选已经读取但尚未处理时，先完成处理再继续搜索。新增 dismiss_candidate：必须引用已读取职位的原文，并记录排除理由；仅对当前用户轮次有效。这是模型选择记录，不是确定性资格判定。
- 保留完整 JD，同时在压缩结果中直接保留标题、公司、地点及最多 8 个带偏移的原文片段。片段不完整，不能替代完整资格证据。
- 搜索卡片按用户请求中的角色词重合度排序，不丢弃未知候选。
- update_plan 的 schema 明示字符串数组和长度限制；错误反馈提供正确格式，不放宽非法参数验证。
- 真实测试自动保存完整 provider 元数据账本，避免只凭末尾 history 统计调用量。

两轮均为合成简历、纽约初级 Data Analyst、目标 15 个 / 至少 10 个合格推荐，Treg 关闭；上限均为 60 provider 请求、100 万输入 token、26 次 MCP 业务调用。

这是两次真实动态数据样本，不是控制变量性能实验。可以确认第一组修复改变了执行轨迹；不能据此保证长期节省比例或长期数据源稳定性。

## 第二轮之后的离线补丁（尚未真实复测）

- API 优先的自动组合评分，在资历证据不足或明确的用户地点未被职位元数据证实时，返回 qualification_needed；不立即导入并调用付费评分。完整正文与不确定候选保留，模型可据证据排除或继续核验。
- 地点解析只覆盖用户明确的“positions/jobs/roles in …”表达；无法解析时不猜测，也不当作通用地理匹配。别名、通勤范围、远程覆盖仍需要进一步核验。
- 明确的 4 年以上经验最低要求覆盖 Junior/New Grad 标题，修复资历判断被标题掩盖的问题。
- 上述是自动路径的费用前置保护，不是所有推荐入口的完整地点强制校验；手动细粒度工具仍需按来源证据处理。

## 离线验证

第一组回归原始记录：111 passed / 1 failed；失败为新增测试假数据源没有 search_directory。补齐测试接口后，新测试 5 passed，相关其余任务流程回归通过。原失败日志保留，不改写为通过。

资格补丁初轮：58 passed / 1 failed；失败说明历史浏览器回放仍允许披露资历未知的备选。将自动付费前置保护限定于本次 API 优先组合路径后，最终相关回归 **133 passed**。原始结果见 `docs/benchmarks/batch-progress-fix-20261012/batch-qualification-final.log`。

## 下一阶段执行顺序

1. 先建立完整的来源资格状态：地点、职位、资历分别记录满足/不满足/未知及原文证据；未知不能计入“合格推荐”配额。保持已获用户授权的备选披露能力，与合格配额分开。
2. 复用现有 score_jobs 入口，对通过资格检查的候选分批评分，共享简历分析与 Jev 上下文；保留每岗结果、取消恢复、嵌套计量和总预算硬门。不要再增加另一个 owner 或 AgentLoop。
3. 用本轮公开岗位样本离线回放，验收少量调用就能排除明显地点/资历问题，并且多个合格候选只提取一次相同简历。
4. 离线完成后再做下一次有限额真实测试。不靠提高额度、降低匹配要求或把远程岗位直接算作纽约岗位取得通过。
