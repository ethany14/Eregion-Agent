# Main 分支：10–15 岗位真实搜索验收（2026-10-12）

## 结论

**FAILED。** 默认 LinkedIn MCP + 招聘板 API 路线可以取得搜索结果和 JD，但本轮没有完成 10–15 个合格岗位的推荐交付。不能把数据源可用等同于 AgentLoop 业务验收通过。

## 可复核的问题

完整工具账本记录 39 次工具调用：`search_jobs` 9 次、`read_job` 12 次、`read_context` 15 次、`update_plan` 2 次、`list_jobs` 1 次。任务快照只保留末尾 24 条 history，因此总计来自完整工具账本，不是末尾快照。

1. **决策没有推进到交付。** 没有任何 import_job、score_job、recommend_job 调用；候选拒绝记录也为空。模型多次宣布即将核验/评分，最后被无进展保护终止。这不证明市场上没有符合条件的岗位。
2. **本轮没有证据支持“主要是 MCP 被挡”。** 所有 11 次 MCP 业务调用成功，未触发登录/限流停止。只是单轮样本，不能据此宣称长期稳定。9 次 search_jobs 工具调用只产生 2 次 MCP 网络搜索，缓存确实避免了重复 MCP 请求；模型轮次仍然被消耗。招聘板分页也包含在 search_jobs 中，不应把每次调用都判为重复网络抓取。
3. **大段 JD 的读取仍消耗过多决策轮次。** read_context 占 15 次。可见记录显示同一 ref 从 offset 0 自动推进到 3000、6000 等；这不等于同一文本被重复返回，但每一段仍额外需要模型决策。
4. **计划工具格式连续错误。** update_plan 传入对象数组，工具要求字符串数组；真实轨迹两次出现这一类调用。需要检查模型可见 schema 与错误恢复，不能只修改验收断言。
5. **候选筛选仍偏宽。** 数据源返回泛分析师、美国远程及纽约周边岗位；当前卡片过滤主要处理明确的资历冲突。模型仍读取了多条与严格 Data Analyst/纽约要求不一致或证据不足的候选。必须保留未知项而不伪造匹配，同时优先处理明确匹配的候选。
6. 招聘板补充路径仍有单页正文提取失败（Stripe 职位 URL）。应单独归因，不能把它计为 MCP 失败。

工具执行合计约 62.7 秒；总耗时 427.77 秒。差值还包括模型推理、持久化、调度等，不能全部标为抓取延迟。

## 推荐下一步

保持唯一 AgentLoop 与 Host owner，先做离线修复，再使用新输出目录复测一次：

1. 核对并修正 update_plan 的模型可见 schema / 调用反馈，覆盖真实错误参数的回归。
2. 在已有候选队列中保存明确的“待读取 / 待资格判定 / 待评分 / 已拒绝及理由 / 已推荐”状态；让导入评分或有证据的拒绝优先于再次搜索，禁止只靠进度文字推进。
3. 对已取得的 JD 一次提供做资格判断所需的标题、地点、资历及对应证据片段。完整 JD 保留按需访问，不要求模型逐个读取固定 3000 字符片段才能继续。
4. 将与用户地点、职位明显一致的候选排序靠前；保持未知项可追溯，不把来源侧的搜索过滤当作最终资格证明。
5. 回归通过后再复测同条件 10–15 岗位；比较合格推荐数、每个合格岗位模型请求数、tokens、总时长、缓存命中和抓取失败。不要仅提高调用上限或降低岗位验收条件。

本次任务没有修改这些业务行为，也没有自动追加第二次付费测试。
