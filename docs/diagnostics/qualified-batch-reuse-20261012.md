# 资格筛选、批量评分复用与严格岗位验收

实现版本：本地 main 的 `e4c28d3`、`9ae5f0d`、`23ac838`。衔接 `batch-progress-fix-20261012.md`；唯一 AgentLoop 与执行 owner 不变。

## 实现

- API 优先路线在单岗、批量评分和推荐入口检查用户请求的职位、地点、资历，逐字段记录满足/不满足/未知与来源证据。未知不计入合格推荐，不触发自动付费评分。这不是对签证等个人条件的全面判定，个人条件仍由后续评分处理。
- `verify_and_score_jobs` 每批最多 8 个已观察 URL，顺序读取来源、资格筛选、复用已有导入，再调用既有 `score_jobs`。不另建执行循环，不自动推荐。
- 批量评分在调用模型前剔除持久化缓存命中；简历、JD 快照、候选事实、模型配置或有效期变化使相应缓存失效。混合新旧岗位只评分新项。沿用 Jev 共享 broker 与总 provider 计量。
- 取消/任务修订检查传播到嵌套 provider 调用前；预算中断保留已导入岗位，恢复时不重复读取和导入。
- 读取正文与成功读取标记的保留上限由 20 调整为 100；正文被淘汰不会抹掉本轮的待核实资格结论。新正文哈希或新用户轮次使其重新核验。
- 大批量结果的普通整包回读返回已有紧凑结论，标记 `no_new_evidence`；具体候选字段和显式历史审计仍可读取原文。
- 接受 `1–2 years' ... experience` / 弯撇号的同义语法。生产与独立验收只修复标点识别，保留原先最多 3 年的范围及更高明确最低年限优先规则。历史验收结果不回写。
- 观察快照保留 LinkedIn 累计成功次数，提醒后续额度耗尽不能抹去之前成功取到的结果。

## 第四轮后收尾修复

`23ac838` 将批次 `no_new_evidence` 从“是否出现过同一个 URL 组合”改为“正文、资格、导入或评分是否真正新增/变化”。换顺序或换组合不会把旧岗位重新算成进展；来源失败也不会伪造进展。预算中断后恢复成功会清除过时失败标记。

最终相关回归 **38 passed**；保留日志 `qualified-batch-final-progress.log`。这个最后补丁目前只有离线证据，未再追加第三次付费复跑，不能拿第四轮数据声称它已通过真实验收。

## 尚需完成

1. 提高候选发现的有效率：先对卡片的明确职位/地点证据做保守筛选，未知保留；避免花详情额度验证大量明显相邻职位。不能直接把 provider 的 entry 标签等同于 JD 已确认初级资历。
2. 对来源返回的正文做带边界、保留原文的清理，排除 LinkedIn 页面推荐职位/申请者统计等非本岗位内容，再验证年限证据；多语言和地理别名需要独立测试，不能通过放宽条件补数量。
3. 完善不足量停止时的交付：给出已验证岗位与明确不足原因，减少在来源额度耗尽后的检索/上下文循环。禁止把已检索到的 LinkedIn 岗位说成从未成功检索。
4. 在上述发现效率和停止行为离线过门后，再执行原条件的 10–15 岗位真实验收。当前不能宣布目标完成，也不继续盲目追加付费样本。

## 边界

地点/角色解析仍是保守的明确表达识别，不是通用多语言地理语义服务；别名、通勤区与远程覆盖不能自动推断。请求/token 上限是实际执行的保护；自定义模型供应商未返回美元账单，模型实际金额未知，不声明零费用或美元硬上限。真实动态样本不能证明长期稳定性。
